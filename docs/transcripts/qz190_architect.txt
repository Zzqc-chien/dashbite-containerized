The Dockerfile alone decides who owns `/data`, and yes, the workers can fail with "permission denied" on first start. The old smoke test would only have caught it indirectly. The prototype also didn't prove this part, because its base image already had `/data` owned by the app user.

Who owns the volume. When Compose first creates the empty named volume, Docker copies the image's `/data` into it, owner included. I checked three cases on the prototype image:

| Situation | Volume owner | Worker (uid 10001) |
|---|---|---|
| Image has `/data` owned by `app`, volume is new | 10001 | writes fine |
| Image has no `/data`, so Docker creates the mount point | root | `PermissionError` |
| Old volume that already holds root-owned files | root, because Docker never re-copies into a non-empty volume | `PermissionError` |

What the failure looks like:
- Each worker creates `/data/raw` and the other folders as its first action, so all four crash at once with `PermissionError: [Errno 13] Permission denied: '/data/raw'`.
- The restart policy turns that into a loop: `make docker-ps` shows `Restarting (1)` on all four workers.
- The dashboard stays `healthy` and shows zeros, because it only reads.
- Health checks never report it, because the processes die before writing their first heartbeat.
- Fixing the Dockerfile and rebuilding won't repair an old volume that already has files; it needs `make docker-clean` first.

What the old plan would have caught. `make docker-test` couldn't catch it, because the tests container mounts no volume. The smoke test only said a `Restarting` row "means a crash loop". And if it was run on a volume left from an earlier session, it never tested first creation at all.

The worker health check reads a heartbeat file. How old can the heartbeat be before a worker counts as unhealthy, and how does that relate to POLL_INTERVAL_SECONDS? How would I test that a worker which is stuck, but still running, is reported as unhealthy?

[AGENT]
I'll check both techniques against the prototype code before answering: freezing a worker with SIGSTOP, and a realistic hang where a worker blocks on a file read.

Both approaches work. Next I'll turn the realistic hang into an automated test in the prototype, to confirm it's fast and reliable before adding it to the plan.

The test catches a real hang in about 3 seconds, on the host and in the image. Now I'll add the threshold explanation and the test to the plan.

A worker counts as unhealthy once its heartbeat is older than `max(30, 3 × POLL_INTERVAL_SECONDS)` seconds. With the demo's 2-second poll that is 30 seconds. You can override it with `HEARTBEAT_MAX_AGE_SECONDS`.

How it relates to the poll interval. Each loop does one round of work, touches the heartbeat, then sleeps for the poll interval. So in a healthy worker the heartbeat is never older than one round of work plus one poll interval. Each part of the formula protects against one mistake:

- The 30-second floor is for fast polls. At a 2-second poll, `3 × poll` would be only 6 seconds, and one slow round would trip it. After an hour of running, re-reading all the feature files once takes about 1.6 s, and train and infer read more than once per round.
- The `3 × poll` part is for slow polls. At a 20-second poll the limit becomes 60 s. Without it, any poll of 30 s or more would fail every probe even when nothing is wrong.

How long until Docker says "unhealthy". Docker waits for 3 failed probes in a row, 10 seconds apart. Counting from the last heartbeat, that comes to about 50–60 seconds with the defaults. In the prototype, a frozen `train` flipped with a heartbeat 57 s old.

How to test a stuck but running worker. I checked all three of these.

- Automated test (new `test_stuck_worker.py`):
  1. It starts `python -m pipeline.preprocess` as a separate process, with a 1-second limit and a 0.1-second poll, and checks the probe returns 0.
  2. It creates an empty named pipe (a FIFO) called `orders_stuck.csv` in `raw/`. Opening a FIFO with no writer blocks forever, so preprocess gets stuck inside `read_csv`. This is a real hang, with no test-only code in the pipeline.
  3. After about 2.5 s it asserts the process is still running and `python -m pipeline.healthcheck preprocess` returns 1.
  It takes about 3 seconds and passed both on the host and inside the image.
- Manual, in containers (smoke test Step 7):
  - Freeze a worker with `docker compose kill -s SIGSTOP train` and wait for `(unhealthy)` in about 60 s. Resume it with SIGCONT and it returns to healthy about 10 s later.
  - Or create the same FIFO inside the preprocess container to hang it in the middle of reading a file.
- Quick manual check on the host: set a 2-second limit, SIGSTOP a worker, and the probe goes from 0 to 1 within 3 seconds, then back to 0 after SIGCONT.

The FIFO check also showed something new. A worker stuck inside a read can't respond to SIGTERM, because it never gets back to its loop to see the stop flag. On the host, the stuck preprocess was still running 2 s after SIGTERM. In a container, Docker would force-kill it after the 10-second grace period. That is the right outcome, and it's now risk R13, with the steps for clearing the FIFO before restarting.

I've added this to the plan: the explanation and table in §3.3, the new test, updated test counts (55 passed, 1 skipped on the host; 53 passed, 3 skipped in the image), and a new acceptance item.
